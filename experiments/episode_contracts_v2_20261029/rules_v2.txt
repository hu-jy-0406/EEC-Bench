You convert an existing v1 evaluation contract for one multi-shot video episode into the v2 layout. This is text work only. Use ONLY the supplied original global and shot prompts (INPUT.prompt) and the supplied v1 contract (INPUT.v1). No tools, outside knowledge, source-video facts or generated outcomes. The v1 contract was compiled from the same prompts and independently audited; keep its requirements unless a rule below says otherwise. Output JSON in the given schema, in English. You output DECISIONS; a program assembles the v2 contract from them and the v1 claims.

ENTITIES (output "entities", in final ID order: all characters first, then all locations, then all objects; IDs are assigned 0,1,2,... in this order).
Only things the prompt names are entities. Granularity rules (owner decisions):
1. Worn or held items (clothing, accessories, phones, weapons, cups, bags, canes, tools...) are SEPARATE entities when the prompt describes any action with or on the item itself: it is the centre of an event (a pistol held to a temple, a cap pulled off and put down, a phone raised to the ear, sunglasses lifted to reveal another pair) or it is handled at all (raised, lowered, moved, shifted, gripped, held up, adjusted, used, written in). Items that are only worn or carried, with no action on the item (a badge on a lanyard, a coat draped over a forearm, a watch on a hand that is lifted, glasses), are NOT entities: they belong in the owner's description. This applies to items v1 listed separately (fold them into the owner) and to items v1 left inside a description (split them out when an action is described).
2. A collection the prompt describes as a group (loose papers, city buildings, a group of desks, guests, a crowd, staff) is ONE entity. Members the prompt describes separately (a front mug and a rear mug; two different pairs of sunglasses) are separate entities.
3. Walls, floors and ceilings are NOT entities; they are part of their location's description.
4. Every other structural part the prompt names is a separate entity: doors, doorways, windows, window frames, grilles, curtains, pipes, valves, wall or ceiling fixtures (sconces, towel rings, lamps), whether or not anything happens to it.
5. All furniture and props the prompt names are separate entities, including background furnishings (shelves, fairy lights) and small items on surfaces (a shaker, a cup, a lamp, desktop papers). If v1 missed a prop, furniture item or structural part that the prompt names, add it (origin "newly_named").
6. Characters include animals and animated sentient actors. Locations are physical settings; reuse one location for an established return; never merge two distinct places.

Each entity: label (character / location / object, no number); name (keep the v1 name for every kept v1 entity; new entities get a stable, distinct, human-readable name that adds no attributes); description; evidence; v1_labels (the v1 labels it continues, [] for a new entity); origin (v1 / split_from_description / newly_named).
DESCRIPTION: the entity's appearance by default in every shot where it appears. Write it from the prompt wording and include EVERY stable appearance attribute the prompt states anywhere in the episode for this entity (colour, material, pattern, shape, size, hair, clothing, accessories that are not separate entities, count of a collection). For a location, include its walls, floors and ceilings as described. Do not add attributes the prompt does not state; do not put shot-specific states, positions or actions in the description. evidence: exact quotes naming or describing the entity (see EVIDENCE).

V1 ENTITY DISPOSITION (output "v1_entities"): exactly one row for every v1 entity label: action kept (target = its own v2 name), merged_into_location (walls/floors/ceilings; target = the location), folded_into_owner (worn/held item without action, or a part that belongs to another entity; target = the owner), merged_into_collection (target = the collection entity); reason (short).

SHOTS (output "shots", one row per shot in order).
- locations: the names of the shot's location(s). Owner rule: list ONLY the main setting where the shot takes place. List two locations only when the camera moves from one location to another within the shot (in the order visited). A place merely visible from the main setting (a hallway seen through a doorway, the sea seen from a beach) is NOT a shot location; it stays in presence. Use [] only if the prompt names no setting for the shot.
- camera_view: ONLY what the shot's prompt states about the camera itself: shot scale (close-up, medium, wide, "a wider view"), camera angle or height, camera position or vantage (over a shoulder, across the desk, reverse view), focus, and the type of composition (two-shot, group composition). Give it as {value, quotes} with exact quotes from that shot's text (or the global prompt); null if not stated. Do NOT restate where entities are, how they are posed or oriented, or what they do (e.g., "the visitor in the central foreground, mostly seen from behind", "A on the left and B on the right"): those remain spatial or motion requirements and must not be duplicated in camera_view or moved there with camera_from_claims. A quote may be longer than the camera information it supports, but the value must contain only the camera information.
- style (filled by the program from the prompt, not by this rewrite): the visual or render style the prompt explicitly states, in its own words; a style in the global prompt applies to every shot, one in a shot prompt to that shot only; null otherwise.
- camera_movement: camera movement, reframing or an explicit instruction to hold the camera steady that the prompt states, same format; null if not stated. Never invent camera information. Actor movement is not camera movement.
- presence: names of every entity expected to be visible in the shot (locations included). Start from the v1 schedule; apply merges (a merged or folded entity is replaced by its target); add split or newly named entities where the prompt makes them visible in that shot. A worn item split out of a description is present in the shots where the prompt mentions it or its owner wears it visibly, until a stated removal.
- absent: names of entities the prompt explicitly says are NOT visible in the shot (v1 presence claims with predicate "absent"); usually [].

CLAIM DECISIONS. The program applies these defaults to every v1 claim:
- presence claims (predicate present): become the shot's presence list (no decision needed, but the entity's target must be in that shot's presence). Presence "absent" claims become the shot's absent list.
- appearance claims: folded into the description of their first entity's target (the description must therefore contain the attribute), unless listed in appearance_keep, camera_from_claims, claim_to_description or dropped_claims.
- spatial and motion claims: kept unchanged as per-shot requirements with entity IDs remapped through v1_entities, unless listed otherwise.
- multi-shot (cross_shot) claims: kept in the top-level cross_shot list, unless listed in camera_from_claims or dropped_claims.
Output only the exceptions:
- appearance_keep: v1 appearance claims that stay per-shot because the attribute is specific to that shot (a state or change in that shot, lighting stated only for that shot, an attribute that differs from the default description) or is explicitly emphasised as a shot requirement. Restating a stable attribute is NOT emphasis. An attribute stated only in the one shot where the entity appears is still a stable attribute and belongs in the description. Give a reason.
- camera_from_claims: v1 claims whose content is purely camera framing/scale/angle/movement (e.g., "both visitors visible from about the waist up"); the field they move into; their content must then appear in that shot's camera_view/camera_movement value. Claims about an entity's position, pose or orientation (on the left, in the foreground, seen from behind) are NOT camera claims; keep them. A claim on how the camera changes between shots ("Shot4 is a closer view than Shot3") stays in cross_shot.
- claim_entity_updates: v1 spatial/motion/cross-shot claims whose entity list must change, e.g., to attach a newly split item ("He lifts a hand to his cap brim" → the man and the cap). REQUIRED for every non-appearance v1 claim that references a merged or folded v1 entity: give the corrected entity list (or use claim_to_description / dropped_claims instead).
- claim_to_description: v1 spatial/motion claims that only describe how a folded item is worn (e.g., "the badge hangs from a lanyard") and now belong in the owner's description; name the entity whose description now contains it.
- dropped_claims: v1 claims that must not be carried over, with a precise reason (only genuine duplicates after a merge, or claims about something that is no longer separately evaluable). Never drop a real requirement.
- new_requirements: requirements the prompt states for split or newly named entities that no v1 claim covers (spatial or motion, or appearance when shot-specific), one shot each, with predicate, expected (atomic, testable), coordinate_frame (none/screen/camera/entity/world), quantifier (exists/start/end/throughout/when_visible), evidence. Do not re-add requirements already present in v1 claims.
- unresolved: keep the v1 unresolved notes that still apply (update entity names) and add genuine new ambiguities only.

EVIDENCE: every quote must be an exact contiguous substring of the named prompt text (fact_id "global" or a shot_id): same spelling, capitalisation, punctuation. No ellipses, no joining of separate phrases; use several shorter quotes instead.

Before returning, check: every v1 label has one disposition; every name you reference exists in entities; IDs are in character/location/object order; no wall, floor or ceiling entity remains; every kept v1 entity keeps its v1 name; every description contains the attributes of the appearance claims folded into it.
