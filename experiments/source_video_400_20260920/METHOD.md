# 400 条候选的执行方法

用户已确认：SF20K 和 MuSS；4/6/8 镜头各 240/120/40 条；每镜头目标 5 秒；保留当前 dense caption；选择性增加机位/景别/运镜描述，保持多样性；排除片尾推广。

原计划依据：`EECBench/docs/dataset-construction-400-v1.md`。本次按每来源 200 条组织，每来源 4/6/8 镜头分别 120/60/20 条。每源作品最终最多 3 条，时间窗口不重叠。电影作品标识从来源标题中可识别的片名年份提取，否则保留视频 ID；不能声称已穷尽识别跨 URL 重传和所有电影别名。

流程：

1. 复用 pilot 官方元数据、下载工具及 40 个原片，新增采集位于本目录。初始扩充到每来源 120 段；不足时继续扩大，成功下载数不是最终候选数。
2. 完整原生帧率解码，保存整数 PTS/帧号。旧片复用经审计的完整时间轴。镜头边界仍为 FFmpeg .10 提案，必须经窗口原帧审核，不能当作镜头真值。
3. 源画面筛查：所有切镜提案的中间帧，开头样本，以及最后 90 秒每 0.5 秒的原帧，制作有精确标识的联系表。独立 Astra/medium 识别推广、订阅/推荐卡、广告、字幕片尾和纯标题段。排除区间向两边留 1 秒余量，片尾推广延伸到源片末尾；不将普通小角标当成广告。
4. 只选完全不与排除区间相交的连续窗口。构造证据一般每镜头头/四分之一/中/四分之三/尾至少 5 帧，长镜头增加原帧；自然机位变化允许，疑似内部剪辑不得强行解释成运镜。
5. 独立新上下文提取 dense prompt，再以独立新上下文核对来源事实、动作时长、身份/出场、物理场景、镜头完整性和每镜头 source_cleanliness。未写入 prompt 的对白/画外原因等不确定性可以保留为限制，不能据此虚构事实，也不自动因此否决整条。
6. 只有 suitable + 独立 pass + 全部必检项 supported 的结果可进入候选。质量拒绝、待修改及调用失败全部留档，不凑数、不把格式有效当作事实有效、不隐去费用。
7. 按配额收集，实际裁出每条候选对应的 source_clips/ 视频供复核，保留原片及精确起止时间。原片不被改写，交付片段不得包含被排除的片尾。
8. 满 400 条后运行 verify_delivery.py：核对完整配额、2000 个逐镜头 prompt、10000 秒目标时长、哈希、来源、审核、广告区间、裁剪时长与源作品上限。只有最终审计通过才发布 candidates_400.jsonl 和 review_400.csv/html。

这是 400 条供用户筛选 300 条的自动审核候选集，不冒充已完成人工审核或生成模型评测。相机术语检测/词数仅为风格诊断，不能替代语义质量检查。没有固定机位描述比例，也不为了多样性编造运镜。

运行均复用现有 Slurm job196092 的空闲 CPU；下载总并发2，源清洁度和 caption/复核调用总并发上限3，视频解码/编码各1线程。campaign.py 是唯一后续构造协调器；不要同时另开源筛查或 caption 协调器。首次并行 source preparation 结束后再交给 campaign 继续准备。

计费记录 usage_cost.json 包含本次源筛查、提取、复核的全部实际 usage，包括质量拦截。按 pricing.json 换算标准 API 等价费用，非账单；缓存输入和 reasoning 均按子集处理。旧 pilot 的24次调用不再次计入。脚本不自动重试已完成/已失败付费调用。

已验证：10 项广告门槛/合同/计费单元测试；旧 UmAV 受推广污染窗口被新排除区间阻止，原帧3189经实际查看确为 Movieclips/Subscribe 推广卡。该单例不是全数据集广告召回率证明。早期 FFmpeg9 filter_script 移除、长选择表达式解析深度、路径类型错误的 CPU 失败日志均归档，未发生对应 API 花费。

2026-09-20 执行修正：源片裁剪改用已安装 FFmpeg 的软件 libopenh264，首两段完整解码及时间误差核查通过，不改变原始证据。来源作品计数使用 source_work_identity.py 的电影名＋年份，识别 Movieclips 旧格式中的 (3/10) 片段编号，不能把片段标题当成片名。已有原片、caption、审计和冻结输入不改写；收集层从原始下载标题重新推导作品键并保留版本。当前元数据检查实际发现两个同片多 URL 组；未识别标题保留视频键并列出人工归并待查，不冒充穷尽去重。相机正则仅用于诊断，修复 medium view / wide composition 等表达漏检，不以正则词数强加固定比例。

MuSS 未识别的作品标题格式保留在 acquisition/source-work 审计中，在完成作品身份归并前不进入候选抽样，避免把无法解析的同片片段当成独立作品。当前检测到4个此类源，原片不删除。准备器新增共享文件锁，可提前以单CPU准备下一批24源；主协调器与预处理器不会同时写同一源。模型并发上限仍为3。

当前优化：H264/AV1/VP9 source_clips 使用经过5窗口逐帧一致性验证的输入端 accurate seek，其他编码保留输出端定位；原始证据不变。8镜头补充提案由 --include-eight-alternatives 显式启用，旧提案和输入保持冻结；替代提案可与未选短提案重叠，但调度同时排除与已交付及同批选中窗口重叠的方案，收集与最终审核再次检查。以当前16个来源的干运行，8镜头提案4→22，广告区间/原帧/最终不重叠/作品配额均通过；这不等于22条已通过事实审核。


## 2026-09-21 — API 并发运行参数更新

原始并发上限为3。检查既有 job196092/node196 低CPU负载和此前调用记录后，下一完整批次起使用 `campaign.py run --batch-size 12 --max-rounds 180 --api-workers 6`；CLI 默认仍为3，可显式回退。源筛查与提取/审核阶段顺序执行，只有一个协调器，各worker最多一个服务调用，总上限6。仅改变运行并发，不改变模型/Astra-medium、prompt、schema、证据、审核/广告 gates、配额、去重/非重叠或视频处理单线程。当前批次完整结束后再切换，无中断/重复提交。保留原有服务失败停止条件；下一批观察服务错误和实际并发，不能预先宣称耗时减半或质量等价验证已完成。快照/校验在 preflight/api-workers6/。

## 2026-09-21 — 用户授权流程去冗余（当前运行方式）

当前命令增加 `--streaming --api-workers 8`。提取 review/reject 显式跳过独立审核（原合同本就禁止通过）；suitable 保留原独立审核。API 任务持续补位，来源筛查与提取/审核共用8名额。采用单候选 manifest，不再等待12条全部完成；期间预留来源/镜头配额、作品上限和不重叠区间，裁剪收集完成后释放。一个CPU线程串行裁剪/收集，与API调用重叠。增量收集和费用合并、仅更新新筛查来源的窗口索引；启动/最终交付保留完整核验。最近12个完成任务中的3次调用失败会停止新增提交并排空在途任务；质量拒绝不计为服务失败。

原模型/提示词/证据/schema/通过门槛及最终 verify_delivery.py 不变。9项模拟测试和真实157条冻结记录重收集一致性检查通过；不是匹配输入的吞吐基准。报告 `preflight/streaming-v1/REPORT.md`。当前进度看 runtime.json 全局活动数，不能把最新单候选manifest当作全流程状态。
